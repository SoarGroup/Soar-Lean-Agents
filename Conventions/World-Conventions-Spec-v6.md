# World conventions for library-based Soar tasks (draft v6)

Supersedes v1 (14 November 2026). Changes from v1: derived object attributes (section 2), the depth limit and flag list (section 6), a section of proposed conventions that await a decision, and the test set and generator notes. Current library: soar-library v2.41; test set v1.34 (16 November 2026; v1.34 corrects the README of v1.33 and v2.41 changes comments only). Revised 16 November 2026, 18:24 (Eastern): sections 1, 6 and 7 and the flags convention brought up to date with library v2.41. The workbook World-Conventions-v6.xlsx is the full list; where this text and the workbook differ, the workbook holds. v3 added the grounding-scope declaration (section 2); v4 changed how relations that decide legality are represented (section 3) and noted the failure-grounding counter (section 2); v5 adds the local-negation convention (section 3) and the open problem of chunking in look-ahead; v6 (15 November 2026) adds literal object handles in task rules (section 2) and updates the chunking problem. Originally based on the restructured libraries (soar-library-restructured v2.3) and the generated tasks that run on them: Counting, Water Jug, Arithmetic, Blocks World, Towers of Hanoi, Eight Puzzle (worldgen v3), plus the four existing conforming programs. Items marked **[library limit]** describe what the library does today, not what it should do.

## 1. Libraries and load order
`soar-library.soar` loads soar-base, selection-world, agent-world, object-world (in that order). Thor (`thor.soar`) is separate. Selection strategy is chosen in `selection-world/strategies/strategies_source.soar`: iterative deepening and first-success are sourced. The separate optimal strategy was retired in v2.15; cost-aware selection now comes from `^flags.cost-metric` and `^flags.optimize` (section 6). All library rules are `:default`, so a task's "user rules" are exactly its own rules.

## 2. World
- Top state has `^world <w>` (made by `initialize-agent-world`: `^anchored-world true`, `^real true`, `^objects`). The task initializes it in `initialize-<task>` (`^task-operator false`), which also sets `^name` and `^desireds`.
- All task entities are `world.objects.object`, each with `^object-handle`, `^anchored true`, `^type`, and its properties as plain attributes.
- Layout switch (generator option): `flat` keeps every property on the object; `static` puts immutable properties (e.g. `type`, `size`, `volume`) under `^static`. A rule must never write a static property. Both layouts give identical behavior on all generated tasks.
- Mutable bookkeeping (e.g. the last block moved, visited-state labels) lives on a `memory`/`history` object in `world.objects`, not on the state.
- **Derived object attributes (new in v2).** An object attribute that an elaboration computes (i-supported) is derived, for example a jug's `free` = volume - contents. Every derived object attribute is listed on the task's problem space, on both problem-space rules (task state and MEA substate): `(<p> ^name water-jug ^dont-copy-object-attribute free)`. No exception for attributes computed only from immutable properties. Workbook row: W-SEL-017 (its wording is narrower: "computed from other properties that can change").
  - Why: the look-ahead world copy copies every object attribute except `object-handle`, `duplicate-of`, `anchored` and the listed ones. An unlisted derived attribute arrives in the copy as a persistent stale value, and the elaboration then adds the recomputed value, so the object holds two values once the look-ahead operator changes its inputs.
  - Symptom: an operator proposed twice with different results, operators proposed that are illegal in that state, and many extra evaluations. Water jug 7/9: 26 evaluations at depth 3 against 14 after the fix; solved 1 of 5 seeds before and 5 of 5 after.
  - The elaboration tests `(state <s> ^world <w>)` with no restriction to one state, so it fires in every world, and its value is a constant (all object attribute values are constants). Unlike a derived relation it needs no `-(<s> ^superstate.world <w>)` guard: firing again for a second state that shares the world gives the same WME.
  - Enforcement: `check_derived.py RULES.soar` reports every i-supported rule that writes an unlisted attribute on a world object. The generator takes `wg.Task(derived=[...])`, emits the list, and refuses to write a task that fails the check.
- **Grounding scope (new in v3, library v2.27).** When a look-ahead failure or the depth limit is reached, the library grounds the result by reading the state, one decision per wme. A task may declare on its problem space the object attributes that determine its state: `(<p> ^name artists ^ground-object-attribute side)`. Grounding then reads, of each world object, only `^object-handle` and the declared attributes. Declare it when the state is fully given by a few changeable attributes (artists: who is on which bank, and the boat's side; the other bank follows). The declaration is a claim that failures depend on nothing else, including the look-ahead path history; a task whose failures do depend on more must list it or declare nothing. Grounding never follows `^duplicate-of` (v2.26). Since v2.28 the default is not to read the state at all (`^flags.failure-grounding counter`): failure and depth-limit results test the world's version stamp (`^applied-count` on the real world, a fresh symbol per look-ahead application), so the scope declaration matters only with `^flags.failure-grounding explicit`.

- **Object handles are tested with `$` in task rules (new in v6; workbook W-CHK-011; generator default).** Every LHS test of an object handle in a task rule is written `^object-handle $ <h>` (also `^argument1.object-handle $ <h>`), so a chunk keeps the handle as a constant. Reason: chunking turns handles into variables and adds no inequality between them, so a chunk learned for one object can fire for another; in Hanoi a chunk learned for moving a disc onto peg P2 also matched the goal peg P3 (FINDING-chunking-overgeneral.md, cause 2). Cost: a chunk transfers only to the same named objects. Two exceptions, because of Soar 9.6.50 defects: no `$` inside a negated condition (Soar reports "bad test type in hash_test ... cannot recover" each time it builds a justification from the rule), and no `$` inside a `{ ... }` test that also holds a relational test, such as `{ <> <bh> $ <dh> }` (segmentation fault). `$` on a variable that a relational test in another condition compares is fine. The generator (worldgen `wg.literalize_handles`, on by default through `Task(literal_handles=True)`) adds `$` only to plain handle tests outside negated conditions. A chunking mechanism that keeps distinct handles distinct would allow transfer across objects; this convention stands until one exists.

## 3. Relations
- A relation is always a relation object: `(<w> ^<rel> <r>)` with `(<r> ^argument1 <obj> ^argument2 <obj>)`, one object per fact. No attribute-points-to-object shortcut and no negated tests on arguments.
- `nothing` is a reserved handle for an empty argument (no negated tests).
- **Maintained, not derived, when it decides legality (new in v4).** A relation or property that decides whether an operator is legal in look-ahead (for example `clear` in Hanoi and blocks world) is created and removed by the operator's application, not derived by an elaboration that tests absence. The task declares it for look-ahead copying: `(<p> ^name hanoi ^copy-relation clear)`; one-argument relations are copied since library v2.29. Reason: a derived relation of this kind is a negation over the look-ahead world, which chunking leaves out of its chunks, and the chunks then prefer illegal or longer paths (FINDING-chunking-overgeneral.md). Maintaining the relation removes that cause; it does not remove the second cause in that finding (wmes that survive because an operator did not touch them), so chunking stays off by default.
- **Avoid testing local negations (new in v5; workbook W-CHK-009).** A rule whose result can reach a chunk should not test the absence of structure in a substate, such as a look-ahead world. One way: maintain such elaborations deliberately, created and removed by the operator applications that change them, and test them with positive conditions. The maintained `clear` above is an instance.
- Other derived relations (not used to decide legality) may still be elaborated on the world.
- Look-ahead copying is by relation name. The library always copies the world relations `on`, `above`, `in` (and handles `holding-object`, `future-event`, `controlled-by`). Any other relation the task needs in look-ahead is declared on the task's problem space: `(<p> ^name <task> ^copy-relation at ^copy-relation adjacent)` (library patch P-004). Do not declare derived relations (those elaborated on the world in every state): they are recomputed in the look-ahead world and a copy would go stale. Declare maintained relations such as `clear`.
- Desired relations of any name are copied into look-ahead desireds as long as they have `^argument1.object-handle` and `^argument2.object-handle` (P-005).

## 4. Desireds
- `^desireds <ds>` with `^desired-count N` and one `^desired <d>` per goal. Goals are object-property desireds `(<d> ^object <o>)` with `(<o> ^object-handle h ^attr value)`, or relation desireds `(<d> ^<rel> <r>)` with `^argument1.object-handle`, `^argument2.object-handle`.
- The task supplies the achieved/unachieved rules (generated: `achievement`, `achievement_relation`); agent-world supplies the counts and `^success`.
- **[library limit]** At most 6 desireds; more raises an error and interrupts. Express larger goals with fewer desireds when a parity or similar argument allows (Eight Puzzle uses 6 tiles).
- Halt: selection-world `top-goal*halt*success*desireds-count`.

## 5. Operators
- Proposed with `^task-operator true`, `^action-handle`, `^argument1`, `^argument2` (objects), `^argument-count`, `^desireds <pre>` with `^desired-count 0`. Propose once per legal move: do not bind a specific unachieved desired in the proposal (that multiplied operators by the number of unachieved desireds). If a proposal's conditions do test a specific desired (a means-ends proposal, workbook W-TOP-010), the operator records it as `^super-desired`; a proposal that tests none has no `^super-desired` (JL, 16 Nov 2026; workbook W-TOP-004). Gate on `^flags.mea-operator-selection true`.
- External application: agent-world writes `^io.output-link.perform-action` with `^name ^argument1 ^argument2` (handles); the task adds one `:o-support` rule applying the effect once per completed command (`^effect-applied`).
- Internal application (look-ahead, `internal-actions true`): a second rule with the same effect.
- Search control: reject rules (`^operator <op> -`). The generated relation tasks reject moving the object moved last, in look-ahead only (`^internal-actions true`).
- Visited-state avoidance is the flag `^avoid-repeated-states` (Water Jug).

## 6. Problem space and flags
- Problem space needs only `^name` (plus the same on the MEA substate). The `^agent-world true` attribute is deprecated (P-006): every task has the agent-world structure, library rules no longer test it, and tasks no longer set it. Tasks written without a world structure must be rewritten to have one.
- Flags stay on the top state. Library defaults (v2.41): agent-world `desired-preferences` false, `gps-desired-ordering` false, `cost-metric` none (unit when `iterative-step` is cost; replaces `use-timers`), `cost-weight` 1, `heuristic-weight` 1, `min-step-cost` 0.01, `rl` false, `smem-store` false, `explore` false; selection-world `optimize` false, `failure-grounding` counter, `aspiration-step` 1, `progress-threshold` 0.15, `hierarchical-properties` false; iterative deepening `iterative-step` operator, `init-evaluation-depth` one, `max-evaluation-depth` 12. A task also sets `mea-operator-selection` and, where it applies, `avoid-repeated-states`. `look-ahead-planning`, `forget-unattended` and `attend-all` are retired (P-009, P-010); `verify` and `guardrails` were removed in v2.38.
- **[library limit]** Iterative deepening stops at `^flags.max-evaluation-depth` (default 12; a flag since v2.37). The `verify` and `guardrails` flags were removed in v2.38. A solution longer than 12 operators from the current state is not found by look-ahead alone.
- Generated tasks run with learning off (Soar's default). For what is known about chunking in look-ahead, see "Chunking in look-ahead" below (workbook W-CHK-010).

## 7. Test harness
Run decision by decision; after each, mark every new `perform-action` complete; stop at `(s1 ^success *)` (`env-complete` mode of run_tests.py). The regression test set is `Soar-library-dev/testset/soar-library-testset-v1.34.zip` (515 tests; its README lists the kinds), run with `python3 run_tests.py --libs <Soar/soar-library>`. The generators are in `Soar-library-dev/tools/worldgen-v19.zip`.

## Open points
- Whether look-ahead copying should stay declared (`^copy-relation`) or become automatic; automatic would need derived relations to be marked, since a copy of a derived relation goes stale.
- Whether the 6-desired limit should be lifted or documented as a limit.

## Flags convention (P-007)

- Flags live on the top state in `^flags` and are copied by pointer into substates (`elaborate*substate*flags`).
- Each project ships a `_flags.soar` file of `:default` rules that set the default value of every flag the project owns: agent-world (`agent-world/_flags.soar`), selection-world (`selection-world/_flags.soar`) and its iterative-deepening strategy (`selection-world/strategies/iterative-deepening/_flags.soar`); the defaults are listed in section 6. object-world has no `_flags` file since `forget-unattended` was retired (P-010).
- A task or personal file never creates `^flags`. It creates `(<s> ^flag-override <o>)` and `(<o> ^<flag> <value>)`. A library rule copies each override into `^flags`; the matching default rule does not fire when an override exists.
- A task normally sets only `^mea-operator-selection true` and any non-default flag (for example `^iterative-step tie-impasse`, `^avoid-repeated-states true`).
- Thor's flag initialization now creates `^flag-override` (not testable here: Thor loading stops at `_firstload`).
- `^agent-world true` on the problem space is deprecated (P-006); every task uses the world structure.
- Test set v1.7: the embedded-variant programs use `*-rules-legacy.soar` (old flags form) because they load the old library copy.

## Rule naming and file layout (P-008)

- Rule names in the four library projects have the form `<project>*<phase>*<topic>[*<detail>]`. `<project>` is the Visual Soar project (`soar-base`, `selection-world`, `agent-world`, `object-world`). `<phase>` is one of `elaborate`, `propose`, `compare`, `apply`.
- The phase is derived from the rule body: `propose` adds an operator with `+`; `compare` states other operator preferences (select, reject, prefer, indifferent); `apply` tests the selected operator (o-support) or halts the agent; everything else is `elaborate`.
- Stray prefixes (`selection`, `evaluate-operator`, `apply`, `world-agent`, `top-goal`, `Impasse__...` and the like) are no longer the first element. Context words that carry meaning (for example `evaluate-operator`, `top-goal`) stay in the topic. Names are lower case with `-` separators; typos in names were corrected.
- Within each file the rules are grouped in the order elaborate, propose, compare (evaluate/compare), apply, with a divider comment between groups.
- Every file starts with a `##` comment and every rule is preceded by a `##` comment. Blank lines are collapsed (inside rules as well). The rule comments are generated from the rule structure plus any prose comment that was already above the rule; they need an author's pass to become real documentation.
- Thor projects (`thor-soar`, `thor-tasks`) received the comments and whitespace cleanup only. Their rules are not renamed or regrouped until the Thor review.
- `rule-renames.csv` maps every old name to its new name; `cleanup-report.txt` lists the 48 rules whose old name used a different phase word than the body shows.
- The `strategies/optimal` and `strategies/first-success` folders are alternatives and intentionally reuse rule names.

## Retired flags (P-009)

- `look-ahead-planning` is retired. It was always true and no library rule tested it. Tasks no longer set it; the one Thor rule that tested it false (`thor-soar*select*operator`, random operator selection) and the Thor initialization line are removed.
- `mea-operator-selection` is kept. It stays true for now, and tasks continue to set it, because a task may need to propose every operator that is satisfied in the current state.
- `forget-unattended` is retired (P-010). It defaulted to false, so the `remove-object` operator (proposal, preference and three application rules in object-world, plus the Thor proposal `agent-world*propose*remove-object*not-desired*hack`) was never proposed; those rules and the Thor flag-initialization line are deleted. object-world no longer has a `_flags` file.
- Retained after review: `rl`, `clean-up-on-success`, `hierarchical-properties`, `task-search-control`.
- Rule names in this document that predate P-008 (for example `top-goal*halt*success*desireds-count`) are now `selection-world*apply*top-goal*halt*success*desireds-count`; `rule-renames.csv` in the library gives the full mapping.

## Duplicates (P-011)

Soar ignores a rule whose body duplicates another rule's (it prints "Ignoring ... because it is a duplicate of ..." while sourcing) and the library tree now has none. Check after any change by loading the library and reading the load log; the build tools include check_load.py.

## Proposed conventions, awaiting a decision (v2)

These came out of the water jug 7/9 comparison (14 November 2026). None is adopted. The generated agents follow them where marked, so that the decision can be made against working examples.

1. **Object attributes are single-valued unless declared.** A world object attribute has one value. An attribute that holds a set (the `visited` labels on the history object) is declared multi-valued. A debug rule file, loaded only in tests, reports any object that holds two values of an undeclared attribute. This check would have reported the stale `free` bug on the first look-ahead step. Not implemented: needs a decision on where the declaration lives (problem space, like `^dont-copy-object-attribute`, or the generator only).
2. **State label for repeated-state avoidance.** A task that avoids repeated states gives each task operator `^result <label>`: the label of the state the operator produces, built from the changeable, non-derived attribute values of all objects in a fixed order (water jug: `7-0`). Apply rules add the label to `history ^visited`; one compare rule rejects an operator whose `^result` is in `visited`, under `^flags.avoid-repeated-states true`. Followed by the generated water jug agents. Cost: each operator is instantiated per parameter binding and apply case so that the proposal can compute the label.
3. **Scope of "repeated".** Open question. As generated, `visited` also keeps every state the agent has actually been in, so the agent never returns to an earlier real state. The classic library and the Lean description (assumption A6) count only the states on the current look-ahead path, from the task state down. The stronger form leaves no way back after a poor move. On water jug 7/9 a poor move cost up to 26 operators against an optimum of 8; the poor moves themselves came from a library rule (FINDING-early-failure-propagation.md), not from this convention.
4. **Known dead-end states.** Two existing forms, to be reconciled: (a) reject the operator by its result label (generated water jug agents; no evaluation substate is created); (b) mark the look-ahead state with a failure (workbook GOL-015, W-LAH-011: `^failure` or `^constraint-failure <desireds>`), which keeps failure knowledge out of operator selection but costs one evaluation per dead end. Only (a) is tested on v2.24.
5. **Learning.** Whether world-convention tasks are expected to run with chunking on. The classic water jug agents get their low decision counts from chunks; the world-convention agents were run without learning.

## Chunking in look-ahead (v6; workbook W-CHK-010)

Status 15 November 2026, library dev (to be v2.30), tie-impasse depth with a cost metric and `^optimize true`, `chunk always`: every water jug (B1, B3, D1, D3), Hanoi and blocks world seed is optimal with chunking, in a first run and in a second run that starts with the first run's chunks; artists-2 is optimal on 2 of 3 seeds in the first run and on all 3 in the second. What made this possible (details in FINDING-chunking-overgeneral.md, update of 15 November): results computed below a depth cut-off carry the cut-off bound into their chunks; a success is returned together with its cost; the failure-cutoff preference names the operator that holds the best value; and object handles are literal (section 2). With the operator iterative step, chunking still gives longer solutions on some water jug seeds. The causes in the v5 text below remain true for rules that do not follow W-CHK-009 and W-CHK-011.

## Open problem: chunking in look-ahead (v5; workbook W-CHK-010)

Chunks learned in look-ahead are over-general, so with chunking on some solutions are longer than optimal (Hanoi 2 discs: 4 or 6 moves on 2 of 6 seeds). Two causes (FINDING-chunking-overgeneral.md): negations over the look-ahead world are left out of chunks (addressed by W-CHK-009 where it is followed), and a chunk does not record that a move left other objects unchanged (not addressed by any convention). Chunking is off by default for look-ahead only as a temporary measure; this is not an accepted end state, and a better way must be found. Candidates, in the finding: grounding success results in the whole declared state so chunks act as a transposition table; explicit frame tests in applications; a positive goal test; changes to chunking itself.

## Corrections of 16 November 2026 (from the workbook review)

- **Failed operators are rejected (library v2.39; W-LAH-014).** An operator evaluated as a failure gets a reject preference, not a worst preference. A top state that holds a losing condition does not halt with success (W-DES-022).
- **Operator-elaboration support (APP-003, OEL-001, OEL-003).** A rule that tests the selected operator and adds to the operator object is i-supported in every action, including actions that change the state (tested in Soar 9.6.6). A rule that changes the state persistently therefore adds nothing to the operator, or is flagged `:o-support`.
- **Elaboration support (ELB-001, ELB-003).** An i-supported WME is removed when its rule no longer matches and no other rule instantiation supports it.
- **Operator names (PRO-001, OPR-006).** `^name` on an operator is a practice, not part of the definition of a proposal. Library rules that print or return evaluations do test it (W-TOP-030), so every tied task operator has one.
- **Look-ahead operator (W-LAH-035, W-TOP-029).** The operator selected in the evaluation state is a shallow copy of the evaluated operator (`^copied-from`); its attribute values still point at real-world objects, so parameters refer to objects by handle.
- **initialize-agent-world (W-WLD-001).** It is proposed while the top state has no `^world`; `initialize-<task>` follows once `^world` exists and the state has no `^name` (W-WLD-026).
- **Wait in look-ahead (W-NOP-005, W-LAH-026): planned.** A state no-change below an evaluate-operator substate means the evaluated operator fails, and no wait is to be proposed there. Library v2.40 still proposes wait there.
- **Reserved attributes.** The rule that task rules must not test selection-world's bookkeeping attributes (W-NAM-012) is withdrawn. Task rules still must not create them (W-NAM-016 for iterative deepening).
- **Terms.** "Attribute" replaces "augmentation" throughout the workbook.
