# Proposed I/O conventions for the standard set (15 November 2026, for review)

Source: issue 5 of Soar-Lean-Agents. Lifted from the world rows (W-WLD-006, W-OUT-003, W-OUT-005, W-APP-003, W-APP-008, W-TIM-002) and generalised off `perform-action` and Thor naming. Demonstrated by `Tasks/Reference/io-guess`. Same columns as `Soar-Conventions.xlsx`; not yet entered there (the workbook has validation formatting that must be edited in Excel). Status: Proposed. IDs follow IO-018.

| ID | Parent | Level | Kind | Strength | Convention | Rationale | If violated |
|---|---|---|---|---|---|---|---|
| IO-019 | IO-005 | L1 Architectural | convention | Must | Interpreted input lands on the task state: elaborations that test `^io.input-link` copy what the task needs onto the state (constants as they are, objects with fresh identifiers, IO-008). All other task rules test the state, never the input-link. | One place holds the mapping; look-ahead and chunking see state structure, not the environment's. | Task rules tied to the environment's names; input aliasing; the task cannot be simulated in look-ahead. |
| IO-020 | IO-006 | L2 Universal practice | convention | Should | The task owns the input mapping. The datamap declares each `^io.input-link` attribute as read-only (IO-006) and names the state attribute it is interpreted into. | A reviewer can see what the environment must supply (compare W-TIM-002). | Undeclared inputs; an environment that omits one fails silently. |
| IO-021 | IO-014 | L2 Universal practice | convention | Should | One command per environment turn. A new command is proposed only when the environment has signalled the next turn (a changed `^turn` or an explicit ready attribute on the input-link) and no earlier command is pending. | Commands are o-supported and the environment answers asynchronously; two pending commands are ambiguous. | Commands overwrite each other; the agent acts on stale feedback. |
| IO-022 | IO-017 | L1 Architectural | convention | Must | An agent in an environment halts on the environment's end-of-episode signal on the input-link (for example `^game-over true`), by an operator application; the agent's own goal is not the end of the episode unless the environment says so. | The environment owns the episode. In the task language `Goal` is terminal, so a goal reached before the environment's signal stops the agent too early. | The agent halts while the environment is mid-episode, or runs on after it ended. |
| IO-023 | IO-022 | L2 Universal practice | convention | May | If the environment starts another episode (a new episode identifier on the input-link), an operator application resets the task state and the pending-command bookkeeping. Otherwise one episode is one agent run. | Repeated play without reloading the agent. | State from the last episode leaks into the next. |
| IO-024 | ORG-007 | L6 Project (constrained) | convention | Must | In a generated agent, hand-written I/O rules are ordinary task rules, kept in files named for their role (`input.soar`, `output.soar`), not in `_escape-*` files. Escape files are for deviations from the conventions (ORG-007, VS-FIL-006). | I/O is first-class Soar; a reviewer skips escape files by the project's own convention. | I/O rules nobody reads; an agent that passes `check` and cannot play. |

Open for the review: whether IO-021 should name `^turn` (as `io-guess` does) or only require "an environment ready signal"; the environments in the corpus use different signals.
