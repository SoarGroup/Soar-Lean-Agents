---

`artists.soar` loads the world libraries and `artists-rules.soar`, which holds 28 task rules. The libraries are agent-world, simple, selection-world and selection-iterative-deepening. `artists-rules.soar` is generated by `gen.py N`, where N is the number of artist–manager pairs (default 3). The English description is a comment at the top of the rules file.

## Running

- **Run the agent:** `python3 run.py [seed]` prints the real crossings, the number of decisions and the CPU time.
- **Check a run independently:** `python3 run.py 1 > out.txt; python3 check.py 3 < out.txt` replays the crossings. It verifies that every trip has one or two people and starts from the boat's side, that no artist is ever left with another manager without their own, and that everyone ends on the right bank.

## Design

- **World:**
  - The banks are `left` and `right`. The boat has `^side`.
  - Each `artist-i` has `^side` and `^manager-handle manager-i`; each `manager-i` has `^side`.
  - The goal is a single desired: the left bank `^empty true`.
- **Task operator `cross`:** moves one or two people from the boat's side to the other bank. It carries `^moves`, `^from`, `^to` and `^argument1..2` under the world conventions.
- **Prediction:** for each proposed crossing, the state holds the side each person would end on and a label for the resulting situation.
  - These live on the state, not the operator. During look-ahead the same operator is acceptable both at the real state and in the evaluation copy, whose worlds differ.
- **Safety:** a crossing is rejected if, on either bank afterwards, an artist is with another manager and without their own.
- **Cycles:**
  - In look-ahead, a crossing that returns to a situation already on the simulated path is rejected.
  - For real crossings, a return to a situation already visited is a worst preference rather than a rejection. The agent prefers progress but can never be trapped by its own history.
- **Search:** ties are settled by iterative-deepening look-ahead. The library's limit is 7 tie levels, which is below the 11 crossings needed for three pairs, so the task raises its top-level limit to 4N−1.
- **No-environment mode:** the program uses lib/world2, the proposed no-environment mode. Crossings update `^world` in the decision they are applied, with no output link and no substates for actions.
- **The boat itself is not constrained**, because the description constrains only the banks.

## Library findings from this program

1. **`propose*initialize-agent-world` tests only `-^name`.** It therefore stays proposed after it has built `^world` and ties with the task's initialization operator. In some seeds a look-ahead applies it a second time and the top state gets two worlds: the search then grinds and never makes a crossing.
   - The task rejects it once `^world` exists.
   - Library fix: add `-^world` to the proposal.
   - mc-world and wizards-world have the same latent exposure.
2. **The look-ahead depth limit is a hard-coded constant.** `^max-evaluation-depth` is 7, or 10 with `^flags.verify true`, which has other effects. A task cannot set it without its own selection-space operator.
3. **Structure built on a superstate's operator from a substate becomes a result of the substate.** An early version put per-world predictions on the tied operator. When the success preference resolved the tie, Soar 9.6.50 crashed in `remove_preference_from_tm`, while removing the goal stack (`remove_existing_context_and_descendents`).
   - This is a kernel defect: the crash should not happen.
   - Keeping such structure on the state avoids it.

## Run with `^iterative-step operator` (10 Nov 2026)

`python3 gen.py 3 operator` makes iterative deepening count every look-ahead operator, instead of counting only tie impasses (the default, `tie-impasse`).

**As shipped, the library decrements the depth once per evaluation state.** In no-environment mode a look-ahead runs many operators in the same evaluation state, and the guard is `-^applied-lookahead true`. The depth therefore never passed 2. Seeds 1–3 still solved safely, but in 21, 19 and 17 crossings (2,000–2,500 decisions, 5–8 s).

**With the guard per operator, the depth counts every crossing.** The fix tests `-^applied-lookahead <o>` and sets `^applied-lookahead <o>`; it is in `lib/selection-iterative-deepening/Impasse__Operator_Tie/evaluate-operator/task-operator.soar`, which is otherwise lib/world2. Results for seeds 1–7:
- **Safety and success:** every run solved, all checked safe.
- **Crossings:** 15, 11, 13, 19, 13, 15, 15 (seed 2 shortest).
- **Cost:** 8,000–65,000 decisions (run with `CAP=150000`), 35–360 s of CPU.

**Iterative deepening still does not find shortest plans here.** Raising the limit from 11 to 13 or 16 changed nothing, so the limit is not what stops it. The likely cause is that ties nested inside a look-ahead get their own depth bookkeeping. Operator stepping costs 15–150 times more than tie-impasse stepping, which runs in about 2 s with median 15 crossings.
